4.2 每個 top-level 目錄的職責

目錄放什麼業界對照
src/應用程式（產品交付給客戶的主程式）Nx apps/、.NET src/
sdk/我們寫的 library（無 GUI、無 exe，可獨立 split）Nx packages/、.NET lib/
sdk/Common/跨元件共用 + vendored third-party（stb 等）.NET Common/、Java common/
sdk/docs/跨元件通用工程經驗（本目錄）—（前端常見每元件自己 docs/）
tools/內部工具 exe / 廠區維護 / 測試用 / 腳本tools/、bin/
tests/純測試（Unit / Integration / Stress 子目錄）tests/、test/、spec/
docs/應用文件（user-manual / 開發者參考）docs/
deploy/現場部署腳本infra/、ops/、scripts/
為什麼沒 top-level third_party/？對齊 Lerna/Nx 派「廠商物品跟著使用者走」原則。 我們只有 stb 一個 vendored lib 跨多處用，放 sdk/Common/（共用層）比 top-level 集中更乾淨。

4.3 sdk/Common/ vs sdk/<元件>/vendor/ 的分界

這是最常見搞混的地方。判斷依據：「有沒有對應的 sdk/ 元件」+「build-time 還是純參考」。

場景放哪理由
廠商 SDK 用來 build（如 stb_image.h #include 進 C++ code）跨元件共用 sdk/Common/<lib>/ application-wide build-time dependency，不專屬任何 sdk/ 元件
廠商規格書 + 範例（對應某個 sdk/ 元件） sdk/<元件>/vendor/ 元件 self-contained，split 帶得走
廠商規格書 + 範例（沒對應的 sdk/ 元件，但未來可能有） 新建殼 sdk/<殼名>/vendor/ 預留未來收 code 的位置（如 sdk/Grabber/）
什麼是「殼目錄」？
有 vendor/ 跟 README.md，但還沒有 <元件>.Core/ code 的 sdk/ 元件目錄。 理由：(1) 預留未來抽出 Bridge.Core 的位置；(2) sdk/ 整體結構統一（vendor/ 一律在 sdk/<元件>/ 內）。

4.4 docs/ vs sdk/docs/ vs sdk/<元件>/vendor/ 的差別

位置內容誰用
docs/user-manual/ 操作員說明（UI 流程、硬體規格、IO 圖） 現場操作員 + 客戶
docs/dev/ 應用層 dev 文件（MIL_API_Reference、system-resources、code review 紀錄） 本專案 dev
sdk/docs/（本目錄） 跨專案可複製的工程經驗（repo style、testing pyramid、FSM） 本專案 + 未來複製到的同類專案
sdk/<元件>/vendor/ 對應該元件的廠商規格書 / 範例 修改該元件 code 時的參考
