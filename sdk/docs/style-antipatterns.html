7. Antipatterns
反模式

這些是 review 時最常見的錯誤，列出來方便引用。

7.1 sdk/ 內 using {AppNamespace};（反向依賴）

反模式 
// sdk/Bridges/LightBridge/LightBridge.Core/LightController.cs
using AniloxRoll.Monitor.Settings;   // ❌ sdk/ 引用了 src/

public LightController(InspectionSettings settings) { ... }
正確做法 
// sdk/Bridges/LightBridge/LightBridge.Core/LightController.cs
// 不引用 application namespace

public LightController(string comPort, int baudRate, byte channel) { ... }
// 應用層自己把 settings 解開傳基本參數進來

為什麼：sdk/ 元件要能獨立 split（變獨立 repo 或 NuGet package）。反向依賴 src/ = split 不出去。

7.2 在 vendor/ 內修改廠商 code

反模式：「我在 vendor/samples/foo.cpp 修了一個 bug，順手 push 上去」
正確做法：vendor/ 保持原樣。需要改的話複製到 sdk/<元件>/<元件>.Core/ 變成「我們的 code」，在那邊改。

為什麼：廠商發新版時，vendor/ 整包替換 → 你的 patch 會被洗掉。 複製到 Core/ 變我們的 code 後，廠商 vendor/ 升級不影響你的修改。

7.3 跨 sdk/ 元件依賴

// sdk/Bridges/LightBridge/LightBridge.Core/LightController.cs
using PlcBridge.Core;   // ❌ 一個 sdk/ 元件引用另一個

三種解法（按合適度）：

  1. 抽共用 sdk/ 元件：把共用邏輯抽到 sdk/Common/Common.Core/，兩邊都引用
  2. 傳基本型別：不要傳 PlcBridge 物件，傳基本參數（int / string / enum）
  3. 應用層做橋接：應用層 src/ 同時引用兩個 sdk/，自己接

為什麼：sdk/LightBridge 要能單獨 split，不能拖著 PlcBridge 一起走。

7.4 廠商規格書放 docs/dev/ 而不是 sdk/<元件>/vendor/

docs/dev/LTS_3DPA24/manual.pdf       ← 應該放 sdk/Bridges/LightBridge/vendor/manual/
docs/dev/Matrox-Grabber/sample.cpp   ← 應該放 sdk/Grabber/vendor/matrox-grabber/samples/

為什麼：未來 split sdk/Bridges/LightBridge/ 時廠商規格書孤兒留在原 repo。 一開始就放對地方，split 時整包走。

例外：third_party/ 內的純 build-time lib（如 stb_image.h）沒對應 sdk/ 元件， 就放 third_party/<lib>/ 是對的。

7.5 sdk/<元件>/ 內放 GUI exe / WinForms csproj

sdk/Bridges/LightBridge/
├── LightBridge.Core/         library OK
└── LightBridge.TestApp/      ❌ WinForms exe 不該在這
    └── *.cs (WinForms)
sdk/Bridges/LightBridge/
└── LightBridge.Core/         純 library

tools/
└── lightbridge-test-gui/     WinForms 測試工具放這
    └── *.cs

為什麼：引用 sdk/Bridges/LightBridge/ 的專案會被迫拉 WinForms 依賴。 sdk/ 純 library（無 GUI、無 exe）才不污染下游。

7.6 元件 self-contained 的反義詞：分散

sdk/Bridges/LightBridge/LightBridge.Core/   code 在這
docs/dev/LTS_3DPA24/                 廠商規格書在這
tests/dotnet_test/LightBridge.Tests/ tests 在這
docs/api/LightBridge.md              API doc 在這

修改 LightBridge 時要跨 4 個目錄翻檔。

sdk/Bridges/LightBridge/                    一個目錄看到全部
├── LightBridge.Core/               code
├── vendor/                          廠商規格書 + 範例
├── tests/                           （也可以放這，或統一在 tests/）
└── README.md                       API doc + 用法
tests/ 該在元件內還是統一目錄？
本專案目前統一在 tests/dotnet_test/<元件>.Tests/（方便 CI 統一跑、InternalsVisibleTo 設定統一）。 這是務實妥協，不完全 self-contained 但夠用。 未來如果某個 sdk/ 元件真的 split 出去，把對應的 test csproj 一起帶走即可。

7.7 正確習慣（總結）

進入 sdk/<元件>/ 目錄後，眼前看到的就是全部 — code、docs、vendor、README。 agent / 新工程師不用跨目錄找東西。 review 時看到「東西放哪」的爭論，回到這條原則。
