E2E Manual Checklist
人工點操作 — 真硬體 + 真 UI

1. 為什麼還是要 manual

WinForms 的 UI 互動很難寫穩定的自動化測試（控制項 hierarchy 變動、async paint timing、跨倍率縮放）。 真硬體（PLC / 光源 / 相機）也沒辦法在 CI 環境模擬。

先用「人工 checklist + 結果勾選」確保可重現的驗證 protocol。E2E 跑同時打開 FSM Action Log 自動驗證 UI transition。

2. 用 HTML + localStorage 寫 checklist

放 docs/user-manual/test-checklist.html，每個 case 一行 <tr> + 三個 button（Pass / Fail / Skip），localStorage 持久化勾選結果跨 reload。範例：

<tr data-case="C01">
  <td>C01</td>
  <td>主畫面 fit：開檔→雙擊→fit→拖曳→雙擊恢復</td>
  <td><button onclick="mark('C01','pass')">✓</button>
      <button onclick="mark('C01','fail')">✗</button>
      <button onclick="mark('C01','skip')">–</button></td>
  <td class="status" id="st-C01"></td>
</tr>
<script>
function mark(id, status) {
  localStorage.setItem('chk-' + id, status);
  document.getElementById('st-' + id).textContent =
    status === 'pass' ? '✓' : status === 'fail' ? '✗' : '–';
}
window.onload = () => document.querySelectorAll('tr[data-case]').forEach(tr => {
  const id = tr.dataset.case;
  const s = localStorage.getItem('chk-' + id);
  if (s) document.getElementById('st-' + id).textContent =
    s === 'pass' ? '✓' : s === 'fail' ? '✗' : '–';
});
</script>

3. 寫 checklist 的 case granularity

  • 每個 case 描述一個「使用者明確會做的動作」+「預期結果」
  • 避免複合 case（測 5 件事一次 → 一個 fail 就無法判斷哪件）
  • 保留人能讀的步驟，不要直接寫 code
  • 步驟之間獨立（不要 case B 依賴 case A 的結果）
配合 FSM Action Log：跑 checklist 時打開 logger（PG 設 DebugUiActionLog=true）， log 寫到 docs/dev/fsm/logs/。跑完後瀏覽器開 viewer.html 一鍵載入， 看哪些 transition 標 ❌（漏列或設計 vs 實作矛盾）。

4. 跟其他層的關係

Level場景
Unit「按鈕 click handler 邏輯」抽出純函式，Unit 驗證
Integration「click handler → Hub.Set → JSON 持久化」整套
E2E（這篇）「使用者點按鈕 → UI 跟著變 → 硬體真的動」
FSM Log跑 E2E 時自動產出 transition 報告
