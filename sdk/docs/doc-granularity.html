Atomic Doc Granularity
文件原子化粒度 — meta-rule，給所有 sdk/docs/ atom 用

原子化文件沒有「最小越好」這回事。太細 → 碎片化、跨檔讀才懂；太粗 → 改一處影響全份、無法 deep-link。這篇是寫 atom 前的判準，避免每次拆 atom 都重新爭論。

1. 兩個判斷維度

維度定義怎麼估
被引用次數 這段內容會被別處（其他 atom / AGENTS.md / skills / PR review）連結引用的頻率 想像 6 個月內，會不會反復用 <a href> 指過來？
相關性 內容之間的耦合 — 改 A 通常也要改 B 嗎？ 看 git history：經常同一個 commit 改的東西就是高相關

2. 2×2 矩陣

                       相關性低                  相關性高
                  ┌──────────────────────┬──────────────────────┐
   被引用高     │  ★ 拆成 atom          │  合成 chapter         │
                  │  (deep-link 友善)     │  (一起讀脈絡才完整)   │
                  ├──────────────────────┼──────────────────────┤
   被引用低     │  扁平段落              │  留在大檔內           │
                  │  (不值得獨立檔)        │  (避免碎片化)         │
                  └──────────────────────┴──────────────────────┘

3. 粒度層級對照

層級檔案數每檔行數用例
Monolith1500+整本書一份 PDF，廠商規格書
Chapter2-5200-500大主題分章
Atom（推薦）5-1550-200一篇回答一個問題
Cell30+< 50wiki 式 micro doc（容易過細）

4. 五個判斷問句

對每段內容問這 5 題，多數答「是」 → 拆出來當 atom；多數答「否」 → 留在大檔內。

問題是 → 該拆
1. 會被別處連結引用嗎？deep-link 友善
2. 未來會被部分複製到其他專案嗎？個別複製方便
3. 不同段落會被不同人/不同時間維護嗎？避免 merge conflict
4. 標題能 standalone 嗎？（不看上下文也說得通）語意完整
5. 超過 200 行了嗎？太大不好讀

5. Heuristic：## 章節 = 一個 atom

實用快速判斷：把內容寫成 markdown 後，每個 ## 大章節 = 一個 atom。 這也是本目錄 style-*.html 採用的粒度（原始大檔有 9 個 ## → 拆成 7 個 atom， 其中 §5 README 模板合進 §4 vendor，§8 反模式 + §9 alignment 各自獨立）。

6. 反模式

過細（Cell）

症狀：
  • 「先點 A 才看得懂 B」— 用 5 個檔案說一件事
  • 檔案多到 index.html 也讀不完
  • 改一個觀念要動很多檔

過粗（Monolith）

症狀：
  • 改一處全份重 review
  • 無法 <a href="big.html#section-7"> 引用（連結不穩定，section id 容易跟著改）
  • 多人同時改卡 merge conflict

7. 實例對照（本目錄 style-* atom 的拆解依據）

內容被引用相關性結果檔案
業界派系對照表 高（onboarding、PR 都會引） 低（自包） ★ 拆 atom style-schools.html
為什麼選 Lerna/Nx 高（決策論據） 高（跟對照表並列） 合 chapter style-choice.html（含論據）
vendor/ 規則 + README 模板 中 高（一起改） 合 chapter style-vendor.html（合 5.1-5.5）
DVT checker 與 raw log 的邊界 高（將來反復引用） 低（獨立 issue） ★ 放產品 owning skill reference .agents/skills/*/references/
Unit / Integration / Stress 測試範例 中 低（不同層） ★ 各自拆 atom 未來 testing-{unit,integration,stress}.html

8. 對未來新 atom 的 checklist

寫新 atom 前先答這 4 題：

  1. 這篇要回答什麼問題？（一句話，超過一句 → 可能該拆兩個 atom）
  2. 誰會看？（onboarding / review 中引用 / PR 論據 / 廠商規格對照）
  3. 會被誰引用？（其他 atom / AGENTS.md / skills / 對話）
  4. 最常一起改的是哪些段落？（一起改的內容該同 atom）

9. 例外：列印 / PDF 場景

如果讀者主要用列印 / PDF（如廠商規格書 review、稽核文件），反而該選 Monolith 或 Chapter。 原子化是給「在線閱讀 + 跨檔引用」場景設計的。對列印場景，一份大檔印一次比較方便。 實務上：線上文件原子化、列印場景用工具合併（pandoc / 自製腳本把 atom 合成 PDF）。
