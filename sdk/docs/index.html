Repo Coding Style

Repo 結構慣例 — 為什麼 sdk/、third_party/、vendor/ 這樣擺。對齊 Lerna/Nx + .NET runtime 派（不對齊 Google monorepo）。

1. Overview — 為什麼有這份 doc 解決多人協作時 repo 結構分歧；決定「對齊 Lerna/Nx 不對齊 Google」的脈絡。 2. Schools — 業界主流派對照 Google / Meta / Microsoft .NET / Lerna/Nx / JetBrains / Amazon 各自的 repo 結構哲學跟適用場景。 3. Choice — 我們的選擇與理由 為什麼小團隊 + 想 split 場景落在 Lerna/Nx 派；為什麼不選 Google。 4. Layout — 具體目錄結構 src/ sdk/ tools/ tests/ docs/ deploy/ third_party/ 分工；sdk/ 跟 third_party/ 的分界。 4b. Layering — 依賴方向（單向 src/→sdk/→third_party/） 為什麼 sdk/ 不能反向 using src/；橫向：跨 sdk/ 元件依賴也是違規；CI lint 一行 grep 檢查。 5. Vendor — vendor/ 子目錄規則 + README 模板 sdk/<元件>/vendor/ 怎麼擺廠商規格書、範例、binary；README.md 必填欄位。 6. Split — 未來把 sdk 元件拆獨立 repo 的流程 git subtree split 步驟；csproj ProjectReference → PackageReference 切換。 7. Antipatterns — 反模式 sdk/ 反向依賴、vendor/ 內改廠商 code、跨 sdk/ 元件依賴、sdk/ 內放 GUI exe。

Meta — 文件寫作風格

給未來新增 atom 時用的判準。所有新文件寫之前先看這篇。

Atomic Doc Granularity — 文件原子化粒度 「被引用次數 × 相關性」2×2 矩陣 + 5 個判斷問句 + 粒度層級對照。決定文件該不該拆 atom 的 SSoT。

Testing & FSM

測試金字塔 + FSM Action Log 自動驗證 UI transition。9 個 atom。

1. Overview — 為什麼四層 + 金字塔 傳統金字塔 + FSM 新層；各層對照表、適合驗證什麼、不適合什麼。 2. Unit Test — 純邏輯 csproj 模板、InternalsVisibleTo、Moq 範例；< 5ms / case，每次 commit 跑。 3. Integration Test — 含 IO JSON round-trip、CSV 寫入、mock 硬體；跟 Unit 的差別表；< 1s / case。 4. Stress Test — 壓力 / Soak STRESS_MINUTES 環境變數控制；找記憶體洩漏、效能退化；不該測功能正確性。 5. E2E Manual Checklist — 人工點操作 HTML + localStorage 持久化勾選；case granularity 原則；配合 FSM Log 自動驗證。 6. FSM Action Log — Design 為什麼 UI state 變 FSM；state-catalog / transition-table CSV 格式；三類標記 ✓/❌/⚠/○。 7. FSM Action Log — Implementation UiActionLogger.cs + ComputeStateId() + viewer.html + ★ SetBatch 漏記坑跟 ComputeStateBefore 修法。 8. Playbook — 新專案落地 11 步驟 SSoT 前置 → 4 個 csproj → InternalsVisibleTo → UiActionLogger → CSV → DebugUiActionLog 開關。 9. Antipatterns — 反模式 Unit 測 UI 顯示、Integration 直連真硬體、SetBatch 漏 FSM entry、test 跟背景 loop race 等。
