Layering
依賴方向 — sdk/ 永遠不能反向引用 src/

1. 三層分工（單向）

src/  ──→  sdk/  ──→  third_party/
（應用）   （library）  （廠商 SDK）
層內容能引用
src/應用程式（WinForms、CLI、business logic）sdk/ + third_party/
sdk/純 library（無 GUI、無 exe）third_party/ + 同層其他 sdk/（盡量避免，見 §6）
third_party/廠商 lib（stb_image.h 等）（不引用任何上層）

2. 為什麼單向

  • Split 友善：sdk/Bridges/LightBridge 拿出去當獨立 repo 時不會拖著 src/ 走
  • 編譯依賴清晰：底層 build 完才能 build 上層，循環依賴不會發生
  • 測試獨立：sdk/ 的單元測試不需要 src/ 的環境
  • 換上層不影響下層：未來 src/ 從 WinForms 換 WPF / Avalonia，sdk/ 完全不動

3. 反向依賴 = sdk/ 跑去 using src/

反向依賴範例（禁止）： 
// sdk/Bridges/LightBridge/LightBridge.Core/LightController.cs
using AniloxRoll.Monitor.Settings;   // ❌ sdk/ 引用了 src/

public class LightController
{
    public LightController(InspectionSettings settings)
    {
        var port = settings.LightComPort;   // 拿應用層物件
        ...
    }
}

為什麼是 split blocker：當你想把 sdk/Bridges/LightBridge/ 拿出去當獨立 NuGet 時， 新 repo 沒有 AniloxRoll.Monitor.Settings，整包編譯不過。

4. 正確設計：只接基本型別

// sdk/Bridges/LightBridge/LightBridge.Core/LightController.cs
// 不引用任何 application namespace

public class LightController : IDisposable
{
    public bool Connect(string comPort) { ... }
    public void SetBrightness(byte value) { ... }
    public void TurnOn() { ... }
}

sdk/ 永遠只看到「200」這個數字，不知道 200 是來自 PG、JSON、CLI 還是別的地方。 這個無知是特性，不是 bug — 它讓 sdk/ 能跨專案重用。

5. 應用層怎麼接

實際 call chain（光源開燈）：

PropertyGrid 「亮度=200」
  ↓ (PG raise event)
src/ SettingsHub.Set(LightBrightness, 200)
  ↓ (Hub.Changed event)
src/ LightControllerService.OnSettingChanged(c)
  ↓ 拆 settings 取 brightness 純數字
sdk/ LightController.SetBrightness(200)
  ↓ RS-232
硬體

應用層（src/）的責任：把 settings 物件解開成基本參數傳給 sdk/。 sdk/ 永遠不接觸 settings 物件本身。

6. 橫向違規：跨 sdk/ 元件依賴

反向依賴是「往上引用」違規。橫向也有違規 — sdk/ 元件之間互相引用：

// sdk/Bridges/LightBridge/LightBridge.Core/LightController.cs
using IoBridge.Core;   // ❌ 一個 sdk/ 元件引用另一個

後果：拆 sdk/Bridges/LightBridge 出去時拖著 sdk/Bridges/IoBridge 一起走，兩個元件變綁定。

解法（按合適度）：
  1. 抽共用：把共用邏輯抽到 sdk/Common/Common.Core/，兩邊都引用底層
  2. 傳基本型別：不傳 IoBridge 物件，傳 int / string / enum
  3. 應用層橋接：src/ 同時引用兩個 sdk/，自己接（最常用）

7. 檢查方式

Repo 任何時候都該保持 sdk/ 乾淨。一行 grep 驗證：

# sdk/ 內不能 using 應用 namespace
grep -r "using AniloxRoll.Monitor" sdk/        # 應該 0 hits

# sdk/ 元件之間不能互相 using
grep -r "using LightBridge"   sdk/Bridges/IoBridge/   # 應該 0 hits
grep -r "using IoBridge"     sdk/Bridges/LightBridge/ # 應該 0 hits
建議在 CI 加一條 lint：每次 PR 跑這幾個 grep，有 hit 就 fail。比 review 時靠人眼抓可靠。

8. 額外 anti-pattern：sdk/ 內接業務 callback

// sdk/Bridges/LightBridge/LightController.cs
public event Action<InspectionResult> OnInspectionResult;   // ❌

InspectionResult 是 src/ 的業務概念，sdk/ 不該知道。

public event Action<bool> OnConnectionChanged;            // ✓ 基本型別
public event Action<byte> OnBrightnessAcknowledged;       // ✓
