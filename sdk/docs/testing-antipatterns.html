Testing Antipatterns
測試金字塔 + FSM 常見反模式

1. 在 Unit Test 裡測 UI 顯示

WinForms 控制項要 message pump，Unit 沒 Application.Run。看到 Assert.That(form.btnSave.Enabled, Is.True) → 升級到 Integration 或 E2E。

2. Integration Test 直連真硬體

真 PLC / 真相機 = E2E，不是 Integration。Integration 用 mock IModbusTcpClient。 真硬體 = 跑 CI 跑不動，現場才能驗證。

3. SetBatch 後忘記補 FSM entry

見 testing-fsm-impl.html §4。SetBatch 不 raise event，logger 看不到，下次 Set 時 stateBefore 是 stale，viewer 誤標 ❌。
修法：OnSettingChanged 開頭加 stale state 偵測（ComputeStateBefore reverse trick），補 (batch) entry。

4. transition-table 跟 ComputeStateId() 不同步

新增第 4 個 setting 但忘記擴充 state-catalog → 所有舊 row 的 from/to id 都對不上。 改 ComputeStateId() 時必須同步改 catalog + table。

5. UI 觸發 inline 跑多個 apply

click handler {
    Hub.Set(A, x);       // 改 state
    Hub.Set(B, y);
    await ApplyA();      // 又跑副作用
    await ApplyB();
}
違反 SSoT view 不互呼。改成「Set 完讓 Changed event 跑 apply」或用 SetBatch + 嚴格 transition 註解。

6. Test 跟背景 loop race（flaky test）

新版 IoGrabController 用 Task.Run + BackgroundLoop（不用 WinForms Timer）。
Test 內呼 await _ctrl.StartAsync(...) 後背景 loop 跑，再手動呼 await _ctrl.PollTick() → 兩個並發 race，flaky test。
修法：SUT 加 internal AutoBackgroundLoop flag 預設 true，test SetUp 設 false 跳過背景 loop。

7. 不寫 InternalsVisibleTo → 改成 public「只為了讓 test 看到」

封裝破壞。改用 InternalsVisibleTo 保持 internal visibility。

8. 正確習慣（總結）

state-centric 設計提問順序：
「這是改哪個 state？」→「副作用是什麼？」→「哪些 view 要更新？」
而不是：「按下按鈕跑哪些函式？」
