1. 為什麼需要四層測試

FSM Action Log（UI transition 自動驗證）
E2E Manual Checklist（人工點操作）
Integration（含檔案 IO / mock 硬體）
Unit（純邏輯 / 無外部依賴）

傳統金字塔只有底下三層。FSM Action Log 是新增層——把「點按鈕 → setting 變更 → 哪些狀態應該轉到哪些狀態」變成可驗證的 transition table，補上 E2E 一直無法用單元測試覆蓋的「人工點操作」邏輯。

層速度覆蓋適合驗證不適合驗證
Unit< 5ms / case純函式、Hub.Set 邏輯、CSV 解析、FSM 邏輯 輸入→輸出的決定性轉換UI 顯示、檔案 IO、time-based
Integration< 1s / caseJSON Save/Load round-trip、CSV 寫入、PlcGrabController FSM + mock IModbusTcpClient 多元件協作 + IO 邊界UI 互動、長時間
Stress數十秒~數小時100 萬筆 Hub.Set / 50 萬 CSV、Soak 24h、PLC FSM 連續循環 記憶體洩漏、效能退化、長時間穩定功能正確性
E2E Manual數分鐘 / 全套主畫面點 chart → mode 切換、PG 改值流程、IO 取像 UI 跨控制項聯動、跨倍率顯示、硬體串接邊界值、回歸測試自動化
FSM Action Log跑 E2E 同時產出state 化 setting 組合 + transition table 對照 「點 X 應該到 Y」自動標 ✓/❌連續行為、效能
關鍵原則：往金字塔上爬，每層成本變高（速度慢、撰寫貴、維護難）。所有能放下層的測試都放下層。
新功能寫測試的問句順序：「這條測試需要設定外部資源（檔案 / mock 硬體）嗎？」→ 是 → Integration ｜「會跑很久（> 1s）嗎？」→ 是 → Stress ｜「都不是」→ Unit。

2. 第一層：Unit Test（純邏輯）

2.1 目的

驗證「純函式級」邏輯的正確性。無 IO、無 await、無 time-based、無 UI。所有對外依賴用 Moq 注入。

2.2 csproj 設定（.NET Framework 4.8 + NUnit 3）

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net48</TargetFramework>
    <LangVersion>7.3</LangVersion>
    <Platforms>x64</Platforms>
    <OutputType>Library</OutputType>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="NUnit"          Version="3.14.0" />
    <PackageReference Include="NUnit3TestAdapter" Version="4.5.0" />
    <PackageReference Include="Microsoft.NET.Test.Sdk" Version="17.8.0" />
    <PackageReference Include="Moq"            Version="4.20.70" />
  </ItemGroup>
  <ItemGroup>
    <ProjectReference Include="..\..\..\src\dotnet\YourApp\YourApp.csproj" />
  </ItemGroup>
</Project>

2.3 InternalsVisibleTo（讓 test 看到 internal 方法）

主專案的 Properties\AssemblyInfo.cs 加：

[assembly: InternalsVisibleTo("YourApp.Tests")]
[assembly: InternalsVisibleTo("YourApp.Integration.Tests")]
[assembly: InternalsVisibleTo("YourApp.Stress.Tests")]
[assembly: InternalsVisibleTo("DynamicProxyGenAssembly2")]  // Moq 需要
反模式：把 internal 改成 public 「只為了讓 test 看到」。改用 InternalsVisibleTo，保持封裝。

2.4 範例：FSM 邏輯 Unit Test（用 Moq 注入 IModbusTcpClient）

[Test]
public async Task FSM_GoesToIdle_OnConnect()
{
    var mockClient = new Mock<IModbusTcpClient>();
    mockClient.Setup(c => c.ConnectAsync(It.IsAny<string>(), It.IsAny<int>()))
              .ReturnsAsync(true);
    var ctrl = new PlcGrabController(mockClient.Object);

    await ctrl.ConnectAsync("192.168.1.1", 502);

    Assert.That(ctrl.State, Is.EqualTo(IoState.Idle));
    mockClient.Verify(c => c.ConnectAsync("192.168.1.1", 502), Times.Once);
}

2.5 分類判斷

  • 用 Mock<I*> 注入 + 純函式驗證 → Unit ✓
  • 用 Path.GetTempFileName() / File.WriteAllText → 改成 Integration
  • for (i = 0; i < 1_000_000; i++) / Task.Delay(minutes) → 改成 Stress

3. 第二層：Integration Test（含 IO / 檔案）

3.1 目的

驗證「多元件協作 + 邊界 IO」是否正常。允許檔案 IO、JSON round-trip、CSV 寫入、mock 硬體。不允許真硬體連線。

3.2 為什麼跟 Unit 分開

差異UnitIntegration
速度< 5ms< 1s（含 temp file 建立 / 寫入）
CI 跑時機每次 commitPR / nightly
依賴純記憶體檔案系統、process
失敗除錯確定性，重跑必同結果可能跟磁碟、權限有關

3.3 範例：JSON Save/Load round-trip

[Test]
public void InspectionSettings_RoundTrip_PreservesAllFields()
{
    var temp = Path.GetTempFileName();
    try
    {
        var original = new InspectionSettings { /* set non-default values */ };
        InspectionSettingsStore.SaveToPath(original, temp);
        var loaded = InspectionSettingsStore.LoadFromPath(temp);

        Assert.That(loaded.Recipe.HessianMaxFactorV, Is.EqualTo(original.Recipe.HessianMaxFactorV));
        Assert.That(loaded.Storage.AniloxRootPath,    Is.EqualTo(original.Storage.AniloxRootPath));
        // 所有欄位逐一驗證
    }
    finally { File.Delete(temp); }
}

4. 第三層：Stress Test（壓力 / Soak）

4.1 目的

找出「跑久了才會出現」的問題：記憶體洩漏、GC 壓力、效能退化、long-tail latency。

4.2 環境變數控制時長

[Test]
public void PlcCommandLoop_NoMemoryLeak()
{
    int minutes = int.TryParse(Environment.GetEnvironmentVariable("STRESS_MINUTES"), out var m)
                  ? m : 1;
    var deadline = DateTime.UtcNow.AddMinutes(minutes);
    var mock = new Mock<IModbusTcpClient>();
    var ctrl = new PlcGrabController(mock.Object);
    long iterations = 0;

    while (DateTime.UtcNow < deadline)
    {
        ctrl.Tick();
        iterations++;
    }

    Assert.That(iterations, Is.GreaterThan(100_000));
    // 配合 dotMemory / PerfView 看 heap，CI 用 STRESS_MINUTES=1 快速跑
}
Soak 跑法：set STRESS_MINUTES=1440 後手動跑單一 [Test]，週末 24 小時 soak。

5. 第四層：E2E Manual Checklist

5.1 為什麼還是要 manual

WinForms 的 UI 互動很難寫穩定的自動化測試（控制項 hierarchy 變動、async paint timing、跨倍率縮放）。先用「人工 checklist + 結果勾選」確保可重現的驗證 protocol。

5.2 用 HTML + localStorage 寫 checklist

放 docs/user-manual/test-checklist.html，每個 case 一行 <tr> + 三個 button（Pass / Fail / Skip），localStorage 持久化勾選結果跨 reload。範例：

<tr data-case="C01">
  <td>C01</td>
  <td>主畫面 fitness：開檔→雙擊→fit→拖曳→雙擊恢復</td>
  <td><button onclick="mark('C01','pass')">✓</button>
      <button onclick="mark('C01','fail')">✗</button>
      <button onclick="mark('C01','skip')">–</button></td>
  <td class="status" id="st-C01"></td>
</tr>
<script>
function mark(id, status) {
  localStorage.setItem('chk-' + id, status);
  document.getElementById('st-' + id).textContent =
    status === 'pass' ? '✓' : status === 'fail' ? '✗' : '–';
}
window.onload = () => document.querySelectorAll('tr[data-case]').forEach(tr => {
  const id = tr.dataset.case;
  const s = localStorage.getItem('chk-' + id);
  if (s) document.getElementById('st-' + id).textContent =
    s === 'pass' ? '✓' : s === 'fail' ? '✗' : '–';
});
</script>

5.3 寫 checklist 的 case granularity

  • 每個 case 描述一個「使用者明確會做的動作」+「預期結果」
  • 避免複合 case（測 5 件事一次 → 一個 fail 就無法判斷哪件）
  • 保留人能讀的步驟，不要直接寫 code

6. 第五層：FSM Action Log（自動驗證 UI transition）

6.1 動機

E2E checklist 的問題：「我點了 chart → 切了 mode → 看起來對」這種「看起來對」沒有客觀標準。如果改了 click handler 邏輯，使用者點下去畫面看起來一樣但**內部 state 跑錯**，checklist 也標 ✓。

解法：把 UI state 編成 FSM（Finite State Machine），所有「(action, fromState) → toState」事先列在 transition-table.csv。runtime 用 logger 記錄真實 transition，跟 table 對比，自動標 ✓ / ❌ / ⚠。

6.2 三個檔案 + 一個 viewer

檔案內容寫一次後
state-catalog.csv列出所有可能 state（n 個 setting 組合出 2^n 個 state）新增 setting 才動
transition-table.csv列出所有預期的 (action, from, to)改 click handler 才動
logs/ui-actions-*.jsonlruntime 寫入，每筆一行 JSON每次 E2E 自動產生
viewer.html瀏覽器開，fetch CSV + 拖入或自動載入 jsonl，自動標一次寫好通用

6.5 Runtime logger（C# 端）

核心類：UiActionLogger。三個 API：

UiActionLogger.SetSource("chartMuraVertical.Click");  // click handler 開頭
UiActionLogger.OnSettingChanged(c);                   // SettingsHub.Changed 訂閱
UiActionLogger.RecordViewOnly("canvasMain.DoubleClick"); // 純視覺操作

核心邏輯：

public static int ComputeStateId()
{
    int b0 = _settings.StitchMode == StitchMode.Global ? 4 : 0;
    int b1 = _settings.EnableMuraEnhance  ? 1 : 0;
    int b2 = _settings.EnableReviewEnhance ? 2 : 0;
    return b0 + b1 + b2 + 1;
}

public static void OnSettingChanged(SettingChange c)
{
    if (!Enabled) return;
    int newState = ComputeStateId();
    string entry = BuildJsonl(_currentSource.Value, c.Name, c.OldValue, c.NewValue,
                              _lastStateId, newState, c.Source.ToString());
    _queue.TryAdd(entry);
    _lastStateId = newState;
}

6.6 viewer.html 顯示三類標記

標記意義
✓ Expected(action, from, to) 在 transition-table — 行為符合預期
❌ Unknown transitionfrom/to 都是 valid state，但組合不在 table — bug 或漏列
⚠ Unknown statestate_id 不在 catalog — setting 組合超出預期範圍
○ View-only純視覺操作（雙擊、拖曳），不改 setting

6.7 ★ 已知坑：SetBatch 不 raise event 會造成假 ❌

常見誤判：如果你的 SettingsHub 有 SetBatch（一次改多個 setting、不 raise event），logger 收不到變更，_lastStateId 不更新。下次 Set 觸發時 stateBefore 是 stale 值，viewer 會誤標 ❌。

實際案例（PICoater AOI 2026-05-21 抓到的）：

10:14:15.877  chartOverview.Click       hd F→T  5→7   ✓
10:14:18.431  chartMuraVertical.Click   hd F→T  7→3   ❌ 假錯誤！

真相：state 7 點 chartMuraVertical 觸發 SwitchReviewStitchModeAndDisableEnhance，內部 SetBatch 改 hb=Vertical + hd=False 但不 raise → state 真的是 7→1，logger 沒記。使用者**接著第二次**點 chartMuraVertical（state 已是 1）→ Hub.Set(hd, true) → 1→3。logger 看到 stateBefore=7（stale），寫成「7→3」假錯誤。

修法

OnSettingChanged 開頭比對 ComputeStateId() vs _lastStateId，不一致補一筆「(batch)」entry：

public static void OnSettingChanged(SettingChange c)
{
    if (!Enabled) return;
    int actualBefore = ComputeStateId() - /* undo current c */;
    if (actualBefore != _lastStateId)
    {
        _queue.TryAdd(BuildJsonl(_currentSource.Value, "(batch)", null, null,
                                 _lastStateId, actualBefore, "Batch"));
        _lastStateId = actualBefore;
    }
    // ...原本邏輯
}

6.8 開關設計（Production 零 overhead）

在 InspectionSettings 加 [Browsable(false)] DebugUiActionLog 預設 false。runtime check：

public static void SetSource(string source)
{
    if (!Enabled) return;  // 預設 Enabled=false，整條 code path 直接 return
    _currentSource.Value = source;
}

Production 不啟用，純 dev mode 開。

7. 新專案落地步驟

7.1 前置：SSoT 架構（必要前提）

FSM 只能套在「SettingsHub 集中所有 state」的專案。如果新專案的 setting 散在 form/control/code 各處改，先做 SSoT refactor，再加 FSM logger。

SSoT 三層分工：

          SettingsHub (state, SSoT)
                  │
        Changed event ↓
  ┌──────────┬──────┴──────┬──────────┐
  ↓          ↓             ↓          ↓
 view A   view B        view C    副作用 (save/reload/...)

規則：

  1. 所有變更走 Hub.Set / SetBatch / NotifyExternalChange，**無路徑直接 _settings.X = ...**
  2. UI 元件是搖桿：點按鈕 = 改 setting，**不在 click handler 內 inline 跑副作用**
  3. 副作用是 view 對 Changed event 的反應

7.2 步驟清單（按順序）

步驟動作產出
1確認專案有 SettingsHub（或 SSoT 等價物）—
2建 4 個 csproj：YourApp.Tests / Integration.Tests / Stress.Tests / UITeststests/ 目錄
3主專案 AssemblyInfo 加 InternalsVisibleTo 四條—
4每個硬體依賴抽介面（IModbusTcpClient...），主程式注入讓 Unit 可 mock
5新增 UiActionLogger.cs（複製 PICoater 版本，改 ComputeStateId()）core logger
6在 SettingsHub.Changed 訂閱 UiActionLogger.OnSettingChanged—
7所有 click handler 開頭加 UiActionLogger.SetSource("xxx.Click")—
8建 docs/dev/fsm/，放 state-catalog.csv + transition-table.csv + viewer.html + README.mdFSM 對照表
9在 InspectionSettings 加 [Browsable(false)] DebugUiActionLog 預設 false開關
10跑 E2E checklist，同時開 DebugUiActionLog=true 產生 logjsonl
11用瀏覽器開 viewer.html，按「載入今天 log」自動對照✓/❌ 報告

7.3 ComputeStateId() 怎麼設計

用 bit 編碼把 n 個 bool / enum 壓成單一整數 + 1：

int b0 = settings.StitchMode == StitchMode.Global ? 4 : 0;  // bit 2
int b1 = settings.EnableMuraEnhance  ? 1 : 0;               // bit 0
int b2 = settings.EnableReviewEnhance ? 2 : 0;              // bit 1
return b0 + b1 + b2 + 1;  // 1..8 (1-indexed for human readability)

3 個 bool/enum = 8 state。state-catalog.csv 列舉這 8 個 row。

+1 是為了讓 state_id 從 1 開始（人看 catalog 比較直觀，0 容易跟「未初始化」混淆）。

7.4 transition-table 怎麼填

對每個 click handler，回答兩個問題：

  1. 「在 state X 點這個 → 應該到 state ?」（n 個 state 就 n 個 row）
  2. 「有沒有 view-only 互動？」（如雙擊 fit、拖曳） → 列 (action, X, X) 表示無 state 變化

不必一次填全，**沒填的 action 跑下去 viewer 會標 ❌「unknown transition」自動提示你補**。

8. 反模式 / 常見錯誤

反模式 1：在 Unit Test 裡測 UI 顯示

WinForms 控制項要 message pump，Unit 沒 Application.Run。看到 Assert.That(form.btnSave.Enabled, Is.True) → 升級到 Integration 或 E2E。

反模式 2：Integration Test 直連真硬體

真 PLC / 真相機 = E2E，不是 Integration。Integration 用 mock IModbusTcpClient。

反模式 3：SetBatch 後忘記補 FSM entry

見 §6.7。修法：在 OnSettingChanged 開頭加 stale state 偵測。

反模式 4：transition-table 跟 ComputeStateId() 不同步

新增第 4 個 setting 但忘記擴充 state-catalog → 所有舊 row 的 from/to id 都對不上。**改 ComputeStateId() 時必須同步改 catalog + table**。

反模式 5：UI 觸發 inline 跑多個 apply

click handler { Hub.Set(A, x); Hub.Set(B, y); await ApplyA(); await ApplyB(); } → 違反 SSoT view 不互呼。改成「Set 完讓 Changed event 跑 apply」或用 SetBatch + 嚴格 transition 註解。

正確模式：state-centric 設計提問順序

討論時用：
「這是改哪個 state？」→「副作用是什麼？」→「哪些 view 要更新？」
而不是：「按下按鈕跑哪些函式？」
