3. Choice
我們的選擇與理由

3.1 條件清單

因素我們的狀況偏好
元件數量4 個 sdk/（AOI_SDK / LightBridge / PlcBridge / StorageBridge）少 → 元件導向
廠商數量3 個（Matrox / LTS-3DPA24 / stb）少 → 不需 third_party 集中
Build toolMSBuild + csproj沒 Bazel/Buck → Google 派工具不適用
未來 split sdk/Bridges/LightBridge/ 出去✓ 明確需求self-contained 派
團隊規模小團隊 + 獨立接案外包結構越自說自話越好

3.2 結論

選 Lerna/Nx + .NET runtime 派。 Google style 是設計給「大規模 + monorepo + hermetic build」的，套小團隊只剩「結構感」沒實質好處。

3.3 不選 Google 的具體理由

  • 沒有 Bazel/Buck：無法強制 hermetic build。Google 風格的 third_party/ 集中是配合 Bazel BUILD 顯式依賴設計的，沒有 build tool 強制，集中只剩「整齊感」沒實質好處。
  • 未來想 split sdk 元件出去當獨立 repo：third_party/ 集中會讓 split 變麻煩（要手動撿對應廠商規格書複製過去），元件 self-contained 才能 git mv 整包走。
  • 4 個元件 + 3 個廠商不夠多：集中沒帶來「找東西比較快」的好處，反而要 cross-reference。
  • 新工程師 / agent 的可讀性：看 sdk/Bridges/LightBridge/ 應該能在這個目錄內看到全部資訊（含廠商 ref），不該跨目錄 jump 才能拼出全貌。

3.4 為什麼 .NET runtime 也影響我們

本專案是 .NET WinForms（不是 npm/Node），所以 Lerna/Nx 不能直接套。但 dotnet/runtime 這個業界最大的 .NET monorepo 也採類似哲學：

  • src/libraries/ 每個 library 自包 src/ tests/ ref/ 子目錄
  • 廠商東西用 NuGet 拉，不放 repo 內
  • 每個 library 可獨立 build / test / package

我們的廠商東西不能用 NuGet 拉（廠商沒上 NuGet），所以折衷：放 sdk/<元件>/vendor/，跟 code 同層。

3.5 跟原本 CLAUDE.md 的關係

本專案的 CLAUDE.md §架構原則：repo 分層 段落已隱含這個選擇（src/sdk/tools/tests/docs 分層、sdk/ 可獨立 split 原則）。本 doc 是「為什麼這樣選」的脈絡展開。
