1. Overview
為什麼有這份 doc

問題

同一個專案組裡的工程師（含獨立接案外包）對 repo 結構的習慣分歧很大。沒有明確規則時會發生：

  • 廠商規格書放 docs/、src/、third_party/、resources/ 各種地方
  • 有人寫 library 放 src/，有人放 lib/，有人放 packages/
  • 測試 csproj 放 tests/、test/、spec/ 都有
  • 共用 utility 散在十幾個目錄
  • review 時花一半時間在「東西該放哪」的格式爭論

這份 doc 的角色

把「repo 怎麼長」變成一個團隊共識，新 agent / 新工程師加入後 5 分鐘看完就知道東西該放哪。

核心精神：對齊「能 split 出去當獨立 repo」的元件導向風格（Lerna/Nx + .NET runtime）， 不對齊 Google monorepo 派。原因見 Choice。

什麼時候用

場景該做什麼
新工程師 onboarding 從 索引 開始順序讀完 1-7 篇 atom
review 時看到「東西放哪」的爭論 引用對應 atom（如 vendor 規則）作 SSoT
新增 sdk/ 元件 看 Layout 跟 Vendor
想 split sdk 元件出去 看 Split
新專案要套用這套 整個 sdk/docs/ 目錄複製過去，照 atom 順序套
