2. 測試方法

第一輪：2 台相機實測

2 台實體相機直接測試，無模擬。混合操作（Live + Review + 存圖 + 參數調整）。

第二輪：模擬 8 台（≈ 7 台）

每台實體相機額外建立 3 組 GPU pipeline + NativeBufferPool，每幀跑 4 次 ProcessImage + 4 組存檔（BMP + JPG）。 2 台 × 4 = 8 條 pipeline。

模擬包含完整 GPU pipeline（AoiService + NativeBufferPool + ProcessImage），但不含 MIL grab/display buffer。 因此 VRAM 數據需從第一輪 2 台實測外推，而非直接取模擬值。

9. GPU 運算分析

處理時間與 fps

情境ProcessMsfps狀態
7 台 效能全開2000~4700 ms0.25~1.0可能不足
7 台 效能平衡130~165 ms~0.9充裕
純回顧合圖 1.3~3.4 s—可接受

降 fps 根因

10000h 模式下，4 次 ProcessImage 在 picoaterLock 內串行執行：

  • 單次 ProcessImage ≈ 500~1200 ms（16384 × 10000 大圖）
  • 4 次串行 ≈ 2000~4700 ms → fps 降至 ~0.25

3000h 模式下單次 ≈ 30~40 ms，4 次串行 ≈ 130~165 ms → fps 維持 ~0.9。

目前 resource log 僅記錄 VRAM（MB），未記錄 GPU 運算使用率（%）。可透過 nvidia-smi utilization.gpu 加入，待後續補充。

15. 已知問題與 Bug

Bug 1：ClearStitchedMode null reference

檔案UI/Presenters/ReviewStitchCoordinator.cs line ~313
現象_ctx.DataStatsPresenter.SetReviewGroupBoxes(false) 在延遲注入尚未完成時觸發 NullReferenceException
修復改為 _ctx.DataStatsPresenter?.SetReviewGroupBoxes(false)
狀態已列入 Plan，待修復

Bug 2：Global 模式下 Mura 垂直圖顯示無意義資料

影響控制項Live: muraChartVerticalLive、Review: chartMuraVertical
現象Global（全域合圖）模式下，mura 垂直圖仍顯示單台相機資料，但此資料在全域合圖語境下無意義
修復Global 模式下清除圖表資料、StitchMode 切換時立即反映
狀態已列入 Plan，待修復

Bug 3：存 BMP 時相機幀率不同步

現象存 BMP 原檔時 Cam1/Cam2 幀率差 3~6 幀（不存 BMP 時完美同步）
原因磁碟 IO 阻塞存檔線程，不同相機的 BMP 寫入耗時不一致
影響單片檢測的時間戳可能略有偏差，但不影響檢測結果
狀態已知限制，非 bug — 不存 BMP 即可避免

Bug 4：10000h 模式 GPU 串行導致 fps 驟降

現象7 台全開模式 fps 從 ~1.0 降至 ~0.25
原因多台相機的 ProcessImage 在 picoaterLock 內串行執行，GPU 無法並行
影響全開模式的即時性大幅降低
狀態架構限制 — 使用平衡模式 (3000h) 可避免

Bug 5：GPU 使用率未記錄

現象Resource log CSV 記錄了 VRAM (MB) 但未記錄 GPU 運算使用率 (%)
建議透過 nvidia-smi utilization.gpu 或 NVML API 加入
狀態待實作
