2. 測試方法

Phantom Camera 7 台完整模擬架構

2 台實體相機（CAM1、CAM2）取像後，分別將 grab buffer 派發給對應的 phantom（CAM1→{CAM3,CAM5,CAM7}、CAM2→{CAM4,CAM6}）。每隻 phantom 擁有自己完整的 GPU pipeline： MIL Display + ProcBuffer + AoiService + NativeBufferPool（CUDA pinned）+ Resize Buffers + Host I/O Buffers，唯一缺少 grab buffer / digitizer。

每個 grab cycle 包含 7 次 ProcessImage、7 次 display 刷新、7 次 Global merge clip、7 份存檔（共用 sharedNow 檔名），與真實 7 台運作幾乎一致；唯一差異是 PCIe / CameraLink 頻寬只反映 2 個 grabber，CameraLink 頻寬上限與 grabber 中斷頻率仍需以實機 7 台另行驗證。

資源量測機制

  • RAM：Process.WorkingSet64（per-process，已排除其他應用）
  • VRAM：Windows Performance Counter「GPU Process Memory \ Dedicated Usage」過濾本程式 PID（per-process，已排除 Chrome/DWM 等）
  • GPU 使用率：nvidia-smi --query-gpu=utilization.gpu（system-wide，2 秒快取；測試時已盡量關閉其他 GPU 應用）
  • CPU：Process.TotalProcessorTime 差分 / 核心數（per-process）
  • 磁碟寫入：BMP 與壓縮檔（jpg+bin）分開累計，CSV 欄位 BmpKB / CompKB / SessionBmpGB / SessionCompGB
  • 每幀寫入 D:\AniloxCaptures\logs\resource-monitor-*.csv

10 分鐘穩定性驗證（Run6）

Run6 連續 10 分鐘 4116 幀後，RAM 第 1 分鐘起穩定於 5.96 GB ± 50 MB，無記憶體洩漏。峰值 6.41 GB（含初始啟動），9.6 分鐘後仍小於 16 GB 規格的 40%。

為何要 2.0× 安全係數：
  • Resource Log 1 秒採樣會錯過 GC Gen2 collection 的瞬間雙倍佔用（LOH 整理時）
  • 開啟 Review tab 一次載入 7 張全解析度影像，spike 1~3 GB
  • Windows 11 Standby Memory 會吃到 RAM 90% 才釋放，超過 80% 觸發 page file swap
  • NVIDIA driver host paging（VRAM 不足時）佔用未列入 working set
  • 長 uptime 後 LOH 碎片化可能讓 working set 慢慢上升
DDR 頻率（DDR4-3200 vs DDR5-5600）對本應用影響可忽略，CPU 穩態僅用 7~22%（平衡）/ 20~25%（全開），記憶體頻寬遠未飽和。雙通道（或更多通道）比高頻率更重要。

5.1 DIMM 配置與通道對齊

現代 Intel/AMD 平台都用 2 的次方倍數通道（2 / 4 / 8），三通道不存在（只在 2008~2011 Intel LGA1366 出現過）。DIMM 數量錯誤會導致通道無法全開，記憶體頻寬大幅下降。

常見錯誤：在 W5-3425 配 4 × 16 GB = 64 GB。看起來容量正確，實際只啟用 4/8 通道，記憶體頻寬從理論 307 GB/s 降到 ~150 GB/s（半頻寬），等同退化成 W5-2445。必須 8 × 8 GB 才能跑滿 8 通道，這是 W5-3425 相對 W5-2445 唯一的核心優勢。
常見錯誤：在 265K 配 3 × 8 GB = 24 GB。Intel Flex Mode 會把 16 GB 跑 dual channel + 8 GB 跑 single channel，有效頻寬 ~75%、且記憶體訪問不對稱，影像 buffer 連續搬運會出現 jitter。永遠插偶數條（2 或 4）。

  • 檢測機本機存圖的 buffer 已含在 working set，2.0× 安全係數已涵蓋
  • 檢測機網路傳輸送端額外 ~150 MB，可忽略
  • 儲存機（收端）需獨立加 500 MB ~ 2 GB，原 8 GB 規格偏緊，建議 16 GB
  • CUDA Pinned Memory 是固定預分配（~500 MB），已含在峰值內

Run3/Run4 的 15.3 GB 不是「剛好塞進」，而是 NVIDIA driver 觸頂自動 throttle 的穩定值。 當 GPU 配置請求超過實體 VRAM 時，driver 不會 OOM，而是啟動 host memory paging（把部分 buffer 搬到系統 RAM 透過 PCIe 取用），並降低 GPU/fps 以維持運作。Run3/Run4 同時出現的症狀都是 throttle 證據：
  • fps 從 ~1.0 降至 0.18~0.21（5 倍降幅）
  • GpuPct 100% 飽和（含 PCIe paging overhead）
  • GpuMs p95 跳到 1191~2538 ms（單次 ProcessImage 理論僅 ~70 ms）
  • CAM1 鏈落後 CAM2 鏈 30%（pipeline 越長 PCIe 流量越大）
  • RAM 從 ~17 GB 暴漲到 25.97 GB（host paging 約 ~9 GB）
所以 Run3/Run4 看到的 15.3 GB 是 driver 上限，不能當作真實 VRAM 需求。真實需求必須從 Run1/Run2 的未 throttle 數據外推。

13. 元件壽命預估

整機壽命瓶頸排序（依先壞順序）：
  1. SSD（容量優先） — Run2 模式 50 天 / 4 TB SSD 寫滿，容量耗盡先於 TBW 耗盡（必須定期清理或網路備份）
  2. LED 驅動板（大陸製）— 4~6 年，可能早於 LED 燈芯先壞，必備備品
  3. LED 光源 (~5.7 年) — 連續 100% 運轉，標稱 50,000 h L70；4~5 年起亮度下降明顯，需更換或補償曝光
  4. HDD（若有） — 5~7 年強制汰換
  5. 散熱風扇 — 5~7 年首次更換，最早的機械故障點
  6. PSU 電容 — 10~12 年，鼓包前通常有徵兆
  7. CPU / GPU 半導體 — 10+ 年，幾乎不會是瓶頸
結論：整機在「定期保養 + 5 年大保養」前提下，瓶頸落在 LED 驅動板（大陸製）4~6 年 與 LED 光源 ~5.7 年，而非 CPU/GPU。建議第 3 年起備妥 LED 驅動板備品、第 4 年起每月監測 LED 亮度（透過 Live mean 值），第 5 年大保養同步更換 LED + 驅動板 + 風扇。若可在休班時段關閉 LED，整機壽命可延至 8~10 年。
計算依據：
  • Thermal cycling 應力以 Coffin-Manson 模型估算，ΔT 從 sustained 84% 改為 23% duty cycle，循環次數降到 1/4，焊球壽命延長約 2~3 倍
  • Electromigration 以 Black's equation：MTTF ∝ exp(Ea/kT)，溫度每降 10°C 壽命延長約 2 倍
  • 風扇軸承壽命為 L10（10% 失效率時間），實際 50% 失效時間約 ×2~3 倍
  • 電解電容壽命遵循 Arrhenius：溫度每降 10°C 壽命延長 2 倍（標稱 105°C 2000h → 65°C 約 32000h ≈ 10 年）

15. 已知問題與限制

限制 1：10000h CAM1 鏈落後（VRAM throttle 引發）

現象Run3/Run4（10000h）下 CAM1 鏈（CAM1,3,5,7）幀數比 CAM2 鏈（CAM2,4,6）少 30~34%
根本原因VRAM 超標被 NVIDIA driver throttle：10000h 真實 VRAM 需求 ~24 GB，超過 RTX 5080 的 16 GB 上限後，driver 啟動 host memory paging（PCIe 搬運 buffer 進出 VRAM）。CAM1 鏈執行 4 次 ProcessImage（CAM1 + 3 phantom），CAM2 鏈執行 3 次，CAM1 鏈每幀的 PCIe paging 流量比 CAM2 鏈多 33%，反壓更強導致 grabber 等待更久
影響10000h 下 7 台取像不同步、fps 從預期 ~1.0 降至 0.18~0.21、CAM1 chain 缺幀。不是純架構問題，是 VRAM 不足的衍生症狀
解法升級至 24 GB+ GPU（RTX 5090 / A6000）消除 paging 後，pipeline 長度差異的影響可降至 <5%。3000h 模式因 VRAM 充足（6.13 GB / 38%），CAM1/CAM2 鏈幀數完全均衡
狀態10000h 必須換 GPU，3000h 不受影響

限制 2：GpuPct 為 system-wide

現象nvidia-smi utilization.gpu 是整張卡的數據，無法區分本程式與其他應用
原因GeForce 消費卡（RTX 5080）NVML 不支援 per-process utilization
應對測試時關閉其他 GPU 應用；VRAM 已透過 Windows Performance Counter 取得 per-process 真實值
狀態硬體限制

限制 3：GpuPct 2 秒快取可能漏記 spike

現象nvidia-smi 查詢成本高，本實作每 2 秒查一次並快取，可能漏記 100 ms 等級的 burst
應對輔以 GpuMs（每幀都記）做交叉驗證；Run3/Run4 GpuMs max 達 1500~2500 ms 即為 spike 證據
狀態已知限制

限制 4：Phantom 共用實體 grabber 影像

現象7 台 phantom 共用 2 個實體 grabber 的同一張畫面，PCIe 中斷與 CameraLink 累積頻寬只反映 2 個 grabber
影響GPU/CPU/RAM/VRAM/Storage 數據可外推；CameraLink 線纜頻寬與 grabber 中斷頻率仍需以實機 7 台另行驗證

限制 5：Run1~5 為短時測試
